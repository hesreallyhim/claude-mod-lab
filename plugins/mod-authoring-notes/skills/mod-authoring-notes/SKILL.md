# Mod authoring notes

Companion to the `plugin-authoring` skill. That skill holds the API; this one holds what the API does not say. Read it after the skill loads and before the first file is written.

These notes were checked on Claude Code 2.1.303. A note that names another version, or says it was not re-run, was not checked on 2.1.303, usually because checking it needs a model request, the desktop app or an organization's managed settings. The API is in early access and changes between releases: where a note and `claude plugin validate`, `claude plugin test` or the declarations the engine writes disagree, they win.

## What the validator refuses

- It reports one refusal in the module's source per run: fix it and run again until it passes.
- `$` is spelled `$.noun.method(...)` at each call site: `$[noun]`, `$?.noun` and a noun taken as a value (`const fs = $.fs`, or passed on) are refused.
- A helper that takes `$` must be a function declaration at the top of the module, a top-level const bound to an arrow or function expression, or a function imported from one of the plugin's own files, and it is called by its name. A closure inside `register` that receives `$` is refused, and so are an alias (`const run = impl`) and a call through a table (`probe.run($)`); hoist the helper, and dispatch with a `switch`.
- An atom's reference needs string literals for `plugin` and `key`. A const holding the plugin name is refused. `read`, `update` and `memberOf` take a source made in the same file (by `atom`, `memberOf` or `derive`): an atom exported to another file does not count there, so share a value through functions of the file that declares it. The variable name given to `$.env.get` or `$.env.set` has to be a literal too.
- A contract (`types/index.d.ts`) imports nothing, and exports at least one type: `export {}` beside the `declare module` block is refused ("a contract exports types and nothing else"), so export the type the state holds. The engine's own types, `StateFamily` among them, are in scope inside its `declare module 'claude-code'` block. A recursive type (a JSON value) in a noun's input fails type-checking through the engine's `Frozen<>` ("Type instantiation is excessively deep"): keep payloads non-recursive, and type an `e` a hook only passes on as `unknown`.
- No dynamic `import()`, in a module or a test file.
- A module imports only code: a `.json` file is refused ("not named like code"), so a mod reads its JSON with `$.fs.read`, from `$.plugin.root` for a file it ships.
- Reading another plugin's state passes, with a note that the state of other plugins was not checked; the validator checks those keys only in a session that has the other plugin enabled.
- A local binding named `next` shadows the continuation and is refused, including a callback's parameter.
- A hook that throws after `next(e)` settled is `kept` when it has no `.catch`: what `next` settled to stands and nothing beneath runs again. With a `.catch`, the handler's answer stands; its `next(e)` replays the unchanged result, so a hook whose work after `next` is the point (a redactor) refuses there instead. A hook that throws before calling `next` is `skipped` and the call goes on as if it were not there, so a guard fails open unless it carries a `.catch` that replays `next(e)` when `next.called` is true and refuses otherwise.
- A `userConfig` field without `title`, `type` (`string`, `number`, `boolean`, `directory`, `file`) or `description` fails `claude plugin validate`; one without `default` passes (give one anyway). A field's /config key is `<name>.<field>`, and its provider is `<name>@inline` for a `--plugin-dir` mod. A change reloads the module with the new `options`, its `$.state` kept.

## Test-kit facts

- The test's `$` has no `state` or `store` noun. Read a mod's state by hooking `on('state.set', { plugin, key })` and recording `e.value`. Serve the store with `mock.store(on)`, or with the test's own `store.get`, `store.set`, `store.delete` and `store.keys` hooks; each op event answers `{ value }` or `{ deny }`.
- An op event nothing in the test answers rejects with "no implementation for <event>", and a hook that lets it throw is skipped. `$.clock` is one: install `mock.clock(on)` before the code under test calls it. `clock.advance(ms)` drives timers.
- Two unmatched hooks on one event in one test fail the module load ("registered twice"). `mock.store` and `mock.clock` register hooks of their own, so do not also hook a store or clock event; vary one helper's behaviour through its options instead.
- A bottom hook returns the event's result shape exactly: `turn.start` returns `{ turnId }`, `session.start` returns `{ cwd }`, `session.end` returns `{ sessionId }`, `command.register` returns `{ value: { command } }`, `prompt.submit` returns `{ text, context }`, `agent.spawn` returns `{ model }`.
- A render test with `$.ui.mount` needs a bottom `ui.render` hook for every path on which the mod's hook yields with `next(e)`. It answers a tree: a plain object such as `{ type: 'Box', children: [] }` stands for a site that draws nothing; `null` counts as no answer. There, `next(e)` answers that bottom tree, where a session answers the engine's own drawing. One instance of a component per surface and `requestId` is mounted at a time; `unmount()` before mounting it again.
- The test's `$` raises engine events only: no `$.fs.read`, no `$.session.cwd()`, no other plugin's noun. To test a call a plugin makes, load an inline plugin beside it, `test(name, { plugins: [{ name, register }] }, body)`, whose command makes the call; a stand-in for another plugin's noun is added the same way, in its `engine.create` hook. The kit loads no `dependencies`: without a stand-in a dependency's noun is undefined, and calling it is a `TypeError`.
- The kit raises no `session.start`, so a command or tool registered there is missing until the test raises it: `$.session.start(...)` with a bottom `session.start` hook that answers `{ cwd }`.
- An inline plugin's `register` runs in a module environment of its own: it cannot read or write the test file's variables ("told is not defined"). It reports through its command's `{ text }`, a `turn.complete` answer, or an op event the test hooks (`ui.toast`), which also tells the test when, mid-stream, a piece reached it.
- A bottom hook on a streaming op event (`process.spawn`) is an `async function*` that yields the pieces and returns `{ value: result }`; a bare result is refused ("returned neither { value } nor { deny }"). The plugin that called reads the result unwrapped from `stream.result`; a hook's `next(e).result` holds `{ value }`. The test's bottom hook resumes after a `yield` only when the hook above asks for the next piece, which is how to check that a hook passes a piece on before pulling the next.
- A test's bottom hook cannot sleep on the kit's clock: the kit refuses `$.clock.sleep` there. To make a call take time, answer a promise the test resolves after `clock.advance(ms)`.
- `findAll` carries a Button's `key` but not a Text's, so a query `{ type: 'Text', key }` finds nothing: find a Text by its `text`, a string or a RegExp. The text is the string as drawn, double spaces included.
- `find` and `findAll` answer elements without their `hover`; `drawn()` answers the whole tree, where a Box's `hover` sits beside its `props`, along with the `group` value a `hover.scope` gives it.
- The kit paints nothing: `$.ui.blit` is the `ui.blit` op event there, recorded or refused by a bottom hook.
- A `Client`'s surface module is driven in the kit through the mounted drawing: `advance(ms)` (its `every` timers), `pointer({ type, x, y, button, in })`, `key({ key, in })`, `post(data)`, and `findAll({ type: 'Text', in: '<key>' })` reads its tree. Type the mount target's `surface` as a literal (a generic helper), or `Mounted` has none of those acts. A surface module sets its state, timers and listeners on its first call (state undefined); the next frame calls it again. In a session, saving it while it is drawn loads it again with its state gone (2.1.302).
- A test file's `console.log` prints, above the results rather than beside its test; a hooks module's prints nothing in the kit. To see a module's value, return it in a command's text or dump it with a failing `expect(...).toBe('')`.
- A plugin's `$.session.compact(args)` reaches hooks in the kit with its arguments alone, no `trigger` or `messages`: a hook that passes `e` on fails there ("messages that are not a list"). Raise `session.compact` from the test's own `$` with the engine's fields to test a compactor.
- The test's `$` raises `prompt.edit`, `prompt.change` and `prompt.autocomplete` at run time though its type does not list them; call them through a cast (`($ as { prompt: { edit: ... } }).prompt.edit(e)`).
- The kit answers `command.register` as the test says, so it misses a name the session refuses: a built-in such as `/focus` or `/plan`, or the plugin's own skill as `/<plugin>:<skill>` (the skill case not re-run on 2.1.303).
- A registered tool answers with a string or an array, never an object: the kit passes an object through, and a session turns it into an error result. Errors are `{ deny }`. The matcher is `mcp__<plugin>__<name>` where `<plugin>` is the manifest name of the plugin the module lives in, so it changes when a mod moves into a larger plugin.
- Prefer arbitrary injected values over copies of real text; a copied real sentence reads as a dependency on it.

## Engine constraints

- Panes, bands, toasts, the status line and `$.ui.log` never reach the model. What does: a tool result's `context`, a `prompt.submit` `context`, a `prompt.compose` section, a registered tool's result, and a command's `{ text }` and `context` (the `context` hidden from the person). Choose one on purpose; a `prompt.compose` section that changes per request defeats the prompt cache.
- The AskUserQuestion site must hold the engine's drawing exactly once, with nothing below it. A render hook may wrap its tree, never replace it. The engine exposes no keypress, focus or selection events for its own dialog: `ui.focus` covers only a pane and the band.
- Returning from a `tool.call` hook while `next(e)` is pending aborts what runs beneath it. That is how a dialog is closed from outside.
- A hook has ten seconds of its own time per dispatch. The clock stops while `next` or any `$` call is in flight, except `$.clock.sleep`, which counts. Race `next(e)` against `$.clock.after`, not against a sleep. Awaiting a promise of the hook's own counts too, one a `$.clock.after` callback resolves included (the call settles once the timer is set), so a long wait waits on a call that stays in flight. At ten seconds the dispatch is abandoned: `next.signal` aborts beneath it and a `.catch` answers the caller then, while the hook's own code may still be running.
- A hook on an op event (`fs.read`, `env.get`) sees every plugin's calls, not only its own plugin's; check `next.origin.plugin` before answering one. Its `e` is normalized first: `$.fs.read('README.md')` arrives as an absolute path with `as: 'text'` filled in, so read paths from `e`.
- `$.prompt.submit` is refused from inside a `command.run` hook because the command holds the turn. Defer it with `$.clock.after`. From a timer it waits until the session is idle, then starts a turn of its own: the transcript heads it "Prompt from the <plugin> plugin", and the model reads it after "The <plugin> plugin sent a message:", so write its text as the plugin's words about the person ("the person asked you"), not as the person's (2.1.303). `$.session.compact` is refused there too, and from a `prompt.submit` hook; a deferral by timer would not reach the plugin's own `session.compact` hook, while another plugin's call between turns (a `$.<noun>` the plugin answers) or the person's `/compact` reaches it.
- `session.compact`'s `messages` split a response into its blocks (a thinking block is an assistant message with no text and no tool calls). A compactor keeping the last n messages must not cut inside a response or leave a tool result without its call. A message the hook builds shows in the transcript like a typed prompt when its role is `user`. A kept first prompt reads to the model as still open unless the summary says it was answered. `/compact`'s own rows are among `messages` as `user` messages: `<command-name>/compact</command-name>`, and an earlier compaction's `<local-command-stdout>` with terminal escapes in its text (the last three on 2.1.302).
- `tool.describe` answers are cached per session. Invalidate them on a setting change and at `session.start`, since a resumed session sends the descriptions it recorded and a mid-session reload keeps the cache.
- `prompt.compose` hooks do not run for an installed plugin under an organization-managed Claude Code (not re-run on 2.1.303).
- Every `$.state.get` in one dispatch reads one moment: after a hook's first read, later reads see its own writes but miss a write another dispatch made meanwhile (a nested call's hook, a queued task). Read after that write has landed, or in a dispatch of its own.
- `$.state` and `$.store` survive a reload; module variables do not. Merge a stored override over the configured defaults rather than trusting its shape, since it may predate a field.
- Another plugin's `$.config.set` passes the owner's `config.set` hook, which may change or refuse the value; the engine then checks what the hooks passed on against the field's `min` and `max`, so a guard that clamps clamps inside them. The `/config` editor refuses an out-of-range number as it is typed, before any hook. A stored value outside them fails the reload, and the previous load stays.
- Built-in tools are not guaranteed present in a session. A mod that needs a model-callable surface registers its own tool with `isDeferred: false`. In auto mode the model called a registered tool with no permission prompt (2.1.303, Haiku); in other modes the person may be asked first.
- A drawing is drawn again by itself only when `$.state` it read changes. One that reads a module variable (a running timer's handle) needs `$.ui.invalidate('ui.render')` after the variable changes.
- `$.audio.play({ asset: 'sounds/chime.wav' })` plays a file the mod ships, its path from the plugin's folder (a `--plugin-dir` mod included), and resolves once the clip has played, so an awaited play holds the hook about as long as the clip (2.1.303, macOS).
- `$.fs.write` creates missing directories. `$.env.set` sets the engine process's environment, which the engine reads live for some settings (the live reading not re-run on 2.1.303).
- The engine's idle timer for the question dialog counts only while the terminal is not focused (not re-run on 2.1.303).
- One plugin, one module: a second `modules` entry is refused by the validator and the session, and two unmatched hooks on one event in one module are refused. Separate mods stay separate plugins.
- A plugin can join a running session: name its folder with `--plugin-dir` at start (an empty folder is fine, a missing one is reported as an error), write the plugin into it later, and run `/reload-plugins`, which a mod can do with `$.command.run({ command: 'reload-plugins' })` from a timer. From inside a `command.run` hook that call is refused, and a headless stream-json session does not offer `/reload-plugins`. The project's `.claude/skills/<name>` works the same way, but only in a folder whose trust prompt was accepted: Claude Code discovers those plugins after trust, so a `-p` session, or one started with `--setting-sources` leaving out `user`, never loads them (2.1.308). Unchanged plugins keep running across the reload.
- A refused `$.command.register` throws, and the rest of the hook that called it does not run: a `session.start` hook that registers a command, then a tool, loses the tool. Register what matters most first, or in hooks of their own.
- A plugin's `dependencies` sit beneath it in every chain, whatever the load order: a mod depending on mod-lab runs above the lab, so the lab's hooks never see its answers. A mod that wants a watcher's eye on its hooks must not depend on the watcher.
- Claude Code expands `:emoji:` shortcodes itself when the closing colon is typed, and lists emoji in the typeahead before a plugin's rows, which then sit out of sight; for `:` tokens, show a hint as `virtualText` ghost text instead of autocomplete rows.
- A `prompt.submit` drop keeps the draft in the box: the box clears, `prompt.submit` runs, and an `engine` `prompt.change` puts the draft back. Its decorations are lost (2.1.302), so a drop message should not point at paint the person can no longer see. A sent prompt's `clear` change comes before its `prompt.submit` (on 2.1.302 it came after), and a registered slash command raises no `prompt.submit` at all; its `command.run` follows the clear by about 10 ms. A `$.prompt.suggest` made in a `clear` hook answers `isShown: false` after a sent prompt or a slash command, and shows after Ctrl+C. A mod that offers a cleared draft back waits a moment after the clear and offers nothing if a `prompt.submit` came.
- Tab and the right arrow at the end of the prompt box raise no `prompt.edit`, so a hook cannot take its own ghost text on them; offer the same completion as a `prompt.autocomplete` row, which Tab takes (a `prompt.change` with origin `engine`). Text that arrives in one write comes as one edit without `key`. The space bar's `key` is `space`, not `' '` (2.1.302).
- A plugin's own hooks see the calls it makes only from inside one of its hooks while that hook runs, not from a timer after it returned or a press handler; other plugins' hooks see them from anywhere. Work whose calls the plugin's own hooks must see goes in a `ui.press` or `ui.input` hook, not in the element's handler. For work another plugin should do inside its own hooks, that plugin adds a noun in `engine.create` and answers the noun's op event; a caller then reaches its hook through `$.<noun>.<method>()`.
- At a render site `next(e)` answers the engine's own drawing, `{ type: 'engine', ref }`, which a hook may place inside a tree of its own: a wrapped row, never a replaced one.
- A transcript row's hook that reads one shared value redraws every row when it changes. A state family keyed by the row's `requestId` (`memberOf(family, e)`) lets each row read and redraw for its own value.
- `$.ui.blit` answers `{ deny }` when the element is not mounted, its size changed, or an `Image` draws its `alt` (no placeholder images inside tmux or screen). Stop an animation after a few refusals in a row and say why. Keep its timer in a module variable: a reload drops the timer, so state saying it plays would be wrong. `$.clock.every` answers `{ cancel }`.
- `display: 'none'` with `hover: { display: 'flex' }` reveals a Box under the pointer with no hook running; a shared `hover.scope` reveals it from another site (a pane glyph lights a band entry). A `Markdown` link is pressable only if `https`, `http` or `file`; a reserved `.invalid` host makes in-pane navigation links.
- `turn.step` chunks a hook yields need `kind`. A trace entry's `chunks` (chunks a streaming link yielded) is absent from every link, in a session on 2.1.302 and in the kit on 2.1.303; count pieces in the hook instead.
- `$.process.spawn` pieces follow the child's writes, not its lines, so split on newlines yourself (2.1.302). A `{ deny }` beneath makes the caller's `for await` throw (`<plugin>: $.process.spawn: <reason>`) and starts no child: wrap the loop. A hook that reads a stream to its end is not cut off by its budget while it waits on pieces (2.1.302).
- A plugin's `$.model.complete` calls do not show in the session's own cost or usage (2.1.302); a mod that spends should meter itself, from each result's `usage`. `model.classify` raises no `model.complete` and answers no usage, so its cost is not visible to a mod at all.
- A cache mark (`{ text, cache: true }` on the last fixed block) pays off on the second call within five minutes: on 2.1.302 with Haiku a 10,567-token prefix was written once and read whole by the next call. A hook answering `model.complete` with `{ value }` sends nothing, which is how a mod or a test stands in for the model.
- The prompt cache's minimum is low (on 2.1.302 with Haiku, a 544-token prefix cached and a ~230-token one did not), so a mod's fixed instructions of a page or two are worth marking. A call's `output_tokens` can exceed its `maxTokens` (129 against 8 was seen on 2.1.302), so a mod bounds its spend by what it asks, not by the cap alone, and gives every model call a `timeoutMs`: waiting on it does not count against the hook's budget.
- At an agent's `turn.complete`, `$.agent.list()` still lists it with its `type` (status `completed`), so a mod can tell its own agents by type, in the kit too, where a spawn answers no `agentId`; seconds later the list drops it. A background agent's answer also starts a main-loop turn. A plugin's `system` row appended from `turn.complete` is stored but not drawn in the fullscreen transcript; `$.ui.log` is (2.1.302). On 2.1.303 a `system` row appended from a timer is stored as `informational` and drawn only in the detailed transcript (ctrl+o), not the normal view: to put something in front of the person, use a toast, the status line, or a `$.prompt.submit` the model answers.
- A spawned agent's answer reaches the main model as a message, besides the spawner's `turn.complete`; spawning adds to what the main model reads. The spawner's own `agent.spawn` hook sees its spawn (the exclusion is the calling hook, not the plugin) (2.1.302). In the kit no spawn starts an agent: `agentId` is set by core alone, a test's bottom `agent.spawn` hook receives the Agent tool's input shape (`subagent_type`, `run_in_background`, where a session's hooks read `subagentType`), and the caller's result names the model it asked for; test a route by what reached the bottom.
- A `session.append` hook reaches the row the model reads, not all the transcript keeps: a tool's structured result (`toolUseResult`, a Read's `file.content`) is stored beside the row untouched. A `tool.call` hook that answers `{ result }` of its own (the record redacted, no `ref` or `text`) is recorded in place of the tool's, `toolUseResult` included: that keeps a secret off the disk. A slash command's output row (`system`, door `command`) is read by the model; a plugin's own `system` row is not (2.1.302).
- In a chain, the engine's link is the `core` tier; in the test kit the test's own hooks are `builtin`. Code that asks whether a call reached the engine reads the tier, and in the kit gets no.
- A text child may not hold a control character or an escape sequence; the engine refuses the whole tree and draws its own, which on the terminal is a blank pane, and says why only in the debug log (the terminal part not re-run on 2.1.303). Strip `\x1b[...` sequences and C0 controls from anything drawn from a transcript, a tool result or a command's output.
- Off the terminal, text is proportional: the desktop app draws `Text` in a proportional face unless it has `mono`, so a grid made of characters (a game board, glyph bars, columns padded with spaces) needs `mono` on each row, or its spaces shrink and the cells stop lining up. The terminal ignores `mono`. The kit's `findAll` returns the prop, so a test can require it.
- A refusal is reproducible in the kit: mount the component against the real data (a fixture module holding the CLI's JSON, since a test may import only its own files and `claude-code`) and `$.ui.mount` reports the engine's reason. Fixtures with clean strings pass while the real pane fails.
- Writing `$.state` inside a `ui.render` hook is refused, since drawing is pure, and the hook is skipped; write from a handler such as `onPress`, or from another event.

## Packaging and installed plugins

- Each enabled plugin's `bin/` folder is appended to the end of the PATH of the session's shell (the Bash tool and `!` commands), not the person's terminal; a command of the same name earlier on that PATH wins.
- A plugin folder with `package.json` and a lockfile (`package-lock.json`, `npm-shrinkwrap.json` or `bun.lock`) gets `npm ci --ignore-scripts --no-audit --no-fund`, or bun's frozen install, into its installed copy at install time. It must finish within 60 seconds and needs npm on Claude Code's PATH. yarn and pnpm lockfiles and `overrides` are refused; with no lockfile nothing is installed.
- A plugin from a local folder marketplace with a relative `source` runs from that folder, so dependencies installed into its cached copy are not there: install them in the folder.
- A marketplace entry can name an npm package as its source. It is unpacked with `npm pack --ignore-scripts`; bundled dependencies come with it, and an `npm-shrinkwrap.json` in it triggers the lockfile install.
- A dependency installs with its plugin, at the same scope. `--config <field>=<value>` at install writes the option to the user settings (`pluginConfigs["<name>@<marketplace>"].options`) whatever the scope. The install may report a `userConfig` option "not yet set" when the field has a default; the default applies.
- Local scope covers a whole git repository, from any subfolder (an install there writes to the root's `.claude/settings.local.json`); outside a repository it covers only that folder.
- Installed plugins stand in each chain in `enabledPlugins` order, project entries before local ones and the first on top, except that a dependency sits just beneath its dependent. Install order therefore decides which installed plugin sees another's answers.
- A plugin loads while a dependency's module is refused, but not when the dependency is neither installed nor loaded ("Dependency "<name>" is not installed" in the debug log, and under Errors in `/plugin` for a `--plugin-dir` copy). An installed dependency satisfies a `--plugin-dir` dependent.
- An installed plugin whose hooks module is refused shows it only in the debug log (`claude --debug-file <path>`): no transcript line, and `/plugin` lists it as enabled with no errors. A `--plugin-dir` copy's refusal is a transcript line. A module that hooks an event the build lacks is refused this way: on 2.1.299 `prompt.change` is not an event.
- Of several copies of one name, one loads: a `--plugin-dir` copy over an installed one (it answers as `<name>@inline`), an installed one over the project's `.claude/skills/<name>`, and of two `--plugin-dir` folders the first given, the second dropped without a message. `--debug-file` says which and why.
- The store is one file per plugin name and origin (`inline`, or the marketplace's name) in the config directory's `plugins/store/`: every `--plugin-dir` copy of a name shares one, so a test session starts with what earlier ones left, and an installed copy has its own.

## Process

- Each mod has a README, and the module's header comment is a few lines pointing at it. Comments state a local constraint or reason, not design history.
- Tests assert behavior through state, text and control wiring, not markup or class names. Counts come from the inputs the test built, not literals.
- Hot reload fires when the turn ends, or sooner when a tool or command the mod registered is about to run. A branched session may not inherit the watch; `claude --plugin-dir <folder>` is the fallback. The desktop app and SDK hosts take the folders from `CLAUDE_CODE_PLUGIN_DIRS` in the `env` block of the user settings (`~/.claude/settings.json`, never a project's), and reload on save only with `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` beside it; that block reaches terminal sessions too (the desktop part not re-run on 2.1.303).
- A pane needs an interactive session; tmux holds one. Type with `send-keys -l "<text>"` and send with a separate `C-m` (an `Enter` beside the text can land as a newline). `C-x` then `Tab` gives a pane the keys, Escape gives them back. `capture-pane -e` keeps colors. SGR mouse reports through `send-keys -l` play the pointer: `\e[<35;<col>;<row>M` hovers, `\e[<0;<col>;<row>M` then `...m` clicks. Kill the tmux session afterwards and check no `claude` process is left.
- `claude -p --plugin-dir <mod> "/<command>"` prints a registered command's answer with no model turn; a `/name` nothing registered goes to the model as a prompt. Several commands in one headless session, state carrying from one to the next: `claude -p --input-format stream-json --output-format stream-json --verbose`, one user message per command; a registered command makes no model request.
- A mod folder copied into a larger plugin keeps its module and contract but takes that plugin's name in atom references, the contract key and the tool matcher. A plugin's `hooks.json` may carry `modules` beside classic command hooks.
- After writing, read the mod's prose and tests as a maintainer would, for wordiness, rhetoric and tests that check more or less than the behaviour, before calling it done.
